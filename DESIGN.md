# QairuCowork — план проектирования

Сайт **и телеграм-бот** для поиска общих свободных окон у студентов одной группы.
Две оболочки одного продукта: общее ядро, общая база, один и тот же человек.

Версия документа: 3.0 · Дата: 2026-09-09

---

## 1. Цель и объём

**Проблема.** Группа студентов в одном чате не может быстро согласовать время встречи: у каждого своё расписание пар, сравнивать вручную долго.

**Решение.** Продукт собирает расписание каждого участника, вычисляет пересечение свободных интервалов и показывает общие окна, а также помогает организовать встречу с голосованием.

**В объёме**
- сбор недельного (повторяющегося) расписания + разовые занятости на дату и на диапазон дат;
- вычисление общих свободных окон для всех или для подмножества участников;
- кворум: окна, где свободны не все, а хотя бы K человек (или K%), с указанием, кого не хватает;
- чётность недель (числитель / знаменатель) с точкой отсчёта от начала семестра;
- буфер на дорогу — расширение каждой занятости на N минут с двух сторон;
- тепловая карта недели и редактор своей занятости мышью и пальцем;
- встреча с опросом (Да / Нет / Предложить изменения), напоминанием и выгрузкой в `.ics`;
- три языка интерфейса: ru / kk / en;
- часовой пояс на уровне группы (по умолчанию Asia/Almaty, UTC+5).

**Добавлено в v3.0 — перенос на Next.js**
- один деплой на Vercel вместо двух процессов: сайт и бот живут в одном приложении;
- бот работает вебхуком и регистрируется сам — из переменных окружения достаточно `BOT_TOKEN`;
- PostgreSQL (Supabase) вместо SQLite; схема совместима с прежней, данные переносятся дампом;
- напоминания о встречах — cron Vercel вместо `JobQueue` живого процесса.

**Вне объёма** (заделы оставлены в архитектуре)
- распознавание расписания со скриншота портала;
- импорт из Platonus / Moodle / ICS;
- подписка на Google Calendar;
- уведомления на почту.

## 2. Ключевые ограничения Telegram Bot API

Это главное, что определяет архитектуру бота. Проектировать «в лоб» здесь нельзя.

| Ограничение | Следствие для дизайна |
|---|---|
| Бот **не может получить список участников группы**. `getChatAdministrators` даёт только админов, `getChatMemberCount` — только число. | Понятие «все участники» = **только те, кто зарегистрировался у бота** (`/join` или переход по deep-link). Бот отдельно показывает, кто ещё не заполнил расписание, и пингует их в чате. |
| Бот **не может написать в личку первым**. Пока пользователь не нажал `/start` — `sendMessage` вернёт `403 Forbidden`. | Регистрация идёт через **deep-link** `t.me/<bot>?start=c<chat_id>`: кнопка в групповом сообщении открывает личку и сразу привязывает пользователя к чату. Все ошибки 403 ловятся и превращаются в подсказку в чате. |
| **Privacy mode** (включён по умолчанию). Бот получает: команды вида `/cmd@bot`; «голые» команды `/cmd` — только если он был последним ботом, писавшим в группу; ответы на свои сообщения; сервисные сообщения. | Privacy mode оставляем **включённым** — приватнее для студентов. Следствие: в чате с несколькими ботами надёжна только форма `/availability@qairucowork` (клиент подставляет `@bot` сам, когда команда выбирается из меню — поэтому `setMyCommands` вызывается при регистрации вебхука). Диалог создания встречи строится на `ForceReply`: ответы на свои сообщения бот получает всегда. |
| Лимиты: ~20 сообщений в минуту на группу, ~1 сообщение в секунду на чат. | Ответы агрегируются в одно сообщение. Пинг незаполнивших — одним сообщением с несколькими упоминаниями, не по одному на человека. |
| `@username` может отсутствовать или измениться. | Упоминания рендерятся как `<a href="tg://user?id=...">Имя</a>` (работает всегда). Username кэшируется в БД и **обновляется при каждом взаимодействии**. |
| Ответ длиннее 4096 символов не отправляется вовсе. | Длинный список окон обрезается по границе строки с честной пометкой. |

Источники: [Bots FAQ](https://core.telegram.org/bots/faq), [Bot API](https://core.telegram.org/bots/api).

## 3. Почему бот и сайт — один продукт, а не два

Соблазн был сделать сайт отдельным приложением со своей базой. Это было бы ошибкой: студент
заполнил бы расписание дважды, и две копии немедленно разошлись бы.

Поэтому граница проведена иначе — **по слою, а не по интерфейсу**:

```
        Telegram                        Браузер / Telegram Mini App
            │                                        │
   app/api/telegram/webhook              app/ (страницы, server actions)
            │                                        │
      src/bot/ (router, handlers)           src/lib/ (auth, group)
            └───────────────┬────────────────────────┘
                            ▼
              src/core/ + src/db/ + src/i18n/
        (не знают ни про Telegram, ни про HTTP, ни про React)
```

Следствия, которые пришлось принять осознанно:

| Решение | Почему так |
|---|---|
| `chats` — это и группа Telegram, и группа сайта | иначе понадобилась бы связка «чат ↔ веб-группа» и синхронизация настроек между ними |
| Группам и людям с сайта выдаются **синтетические id** ниже `−10^15` | Telegram раздаёт пользователям положительные id, а чатам — порядка `−10^12`; выбранный диапазон гарантированно свободен, и один тип `bigint` обслуживает оба мира. `−10^15 − 2^40` остаётся внутри `Number.MAX_SAFE_INTEGER`, поэтому в JS id можно держать обычным числом |
| Аккаунтов на сайте нет | студент не станет заводить пароль ради того, чтобы отметить пары; личность несёт токен в куке |
| `initData` Telegram Mini App проверяется подписью | это единственный способ доказать, что веб-посетитель — тот же человек, что и в боте, не спрашивая ничего у него самого |

## 4. Стек и почему он такой

| Слой | Выбор | Почему |
|---|---|---|
| Фреймворк | Next.js 16, App Router, TypeScript | требование заказчика — деплой на Vercel одним кликом; серверные компоненты дают серверный рендер без отдельного API-слоя |
| БД | PostgreSQL (Supabase) + Drizzle ORM | Vercel не хранит файлы между запросами, поэтому SQLite отпадает. Drizzle — тонкая типизированная обёртка над SQL без кодогенерации и бинарного движка, который на лямбде пришлось бы тащить в бандл |
| Драйвер | `postgres.js`, `prepare: false`, `max: 1` | пулер Supabase в transaction mode не поддерживает prepared statements; одно соединение на функцию — пулер и так держит их за нас |
| Бот | вебхук + собственный клиент Bot API на `fetch` | на Vercel нет живого процесса: long polling невозможен. От `python-telegram-bot` пригодилась бы ровно тонкая обёртка над HTTP, а очередь задач, персистентность и polling там всё равно не работают |
| Состояние диалогов | таблица `bot_state` (JSONB) | замена `PicklePersistence`: между двумя апдейтами одной беседы может пройти любая пауза, и обслуживать их будут разные лямбды |
| Напоминания | cron Vercel + флаг `reminder_sent` | замена `JobQueue`. Флаг ставится до отправки: повторное напоминание хуже пропущенного |
| Стили | Tailwind CSS v4 поверх CSS-переменных | палитра и тепловая шкала заданы токенами на `:root`, тёмная тема переопределяет только их — ни одному компоненту не нужен вариант `dark:` |
| Вход | токен в куке + `initData` Mini App | регистрация убила бы заполняемость — а именно она определяет ценность всего продукта |
| Тесты | Vitest + PGlite | Postgres поднимается прямо в процессе, миграция накатывается тем же файлом, что уедет в Supabase |

## 5. Модель данных

Имена таблиц и колонок совпадают с прежней SQLAlchemy-схемой — базу от Python-версии
можно перелить дампом без переименований.

```
users(user_id PK, username, full_name, lang, is_web, created_at)
chats(chat_id PK, slug UNIQUE, origin, title, lang, tz, day_start_min, day_end_min,
      min_slot_min, travel_buffer_min, semester_start, reminder_min, created_at)
memberships(chat_id, user_id, joined_at)                        PK(chat_id,user_id)
busy_slots(id PK, user_id, weekday 0..6 NULL, specific_date NULL,
           date_from NULL, date_to NULL, week_parity NULL,
           start_min, end_min, label, kind, source)             -- занятость
schedule_state(user_id PK, filled, updated_at)
web_sessions(token PK, user_id, created_at, last_seen_at)
meetings(id PK, chat_id, initiator_id, place, when_text, when_start,
         goal, chat_message_id, invitees, status, reminder_sent, created_at)
meeting_responses(meeting_id, user_id, answer yes|no|change,
                  comment, responded_at)                        PK(meeting_id,user_id)
bot_state(key PK, data jsonb, updated_at)                       -- шаги диалогов бота
```

Замечания:

- `busy_slots` хранит **занятость**, а не свободу: расписание пар — это то, что человеку легко продиктовать. Свободные окна вычисляются как дополнение.
- Одна таблица `busy_slots` покрывает четыре вида занятости, и вид определяется тем, какие поля не NULL:
  `weekday` + `week_parity IS NULL` — каждую неделю;
  `weekday` + `week_parity` 0/1 — через неделю (числитель / знаменатель);
  `specific_date` — разовая (экзамен, отработка);
  `date_from`..`date_to` — период (сессия, поездка), в том числе «весь день» интервалом 00:00–24:00.
  Это дешевле трёх отдельных таблиц и не усложняет выборку: движок всё равно получает плоский список интервалов на день.
- `week_parity` бесполезна без точки отсчёта, поэтому чётность считается от `chats.semester_start`. Если админ его не задал, такие слоты **игнорируются** — это честнее, чем угадывать неделю по номеру ISO и показать неверные окна.
- `schedule_state.filled` отличает «свободен всю неделю» от «не заполнял». Без этой отметки человек, который ничего не ввёл, выглядел бы свободным круглосуточно и молча портил бы расчёт всей группе.
- Время — минуты от полуночи в часовом поясе **чата**, а не пользователя. Для студентов одного вуза это верное упрощение; поле `chats.tz` оставляет путь к мультитаймзонности.
- Расписание принадлежит **пользователю**, а не паре (чат, пользователь): заполнил один раз — работает во всех своих чатах.

### 5.1. Даты и моменты времени — разные типы

Это место, где прошлая версия обжигалась, и здесь оно решено на уровне типов.

| Что | Тип в БД | Тип в коде | Почему так |
|---|---|---|---|
| Календарная дата (`semester_start`, `specific_date`, `date_from`) | `date` | строка `YYYY-MM-DD` | `new Date("2026-09-14")` — это полночь UTC, и в поясе группы она уже вчера. Через `Date` календарные даты не гоняются вовсе |
| Момент времени (`when_start`, `created_at`) | `timestamptz` | `Date` | Postgres хранит смещение сам. В SQLite его приходилось навешивать вручную, иначе время встречи уезжало на пять часов |

Перевод «настенное время группы → момент» делает `zonedWallToUtc()` через `Intl.DateTimeFormat`:
смещение подбирается за две итерации, поэтому переход на летнее время не сдвигает встречу
(закреплено тестом на Europe/Berlin в сентябре и декабре).

## 6. Алгоритм поиска общих окон

Ядро — три чистые операции над списком полуинтервалов `[start, end)`:

1. **`merge(intervals)`** — сортировка по началу, слияние пересекающихся. `O(n log n)`.
2. **`invert(busy, lo, hi)`** — дополнение до рабочего окна дня → свободные интервалы одного человека.
3. **`intersect(a, b)`** — пересечение двух отсортированных непересекающихся списков методом двух указателей, `O(n+m)`.

Полный проход для одного дня:

```
free_common ← [[day_start, day_end]]
для каждого пользователя u:
    busy_u ← merge( слоты u для этого weekday + слоты u на эту дату )
    free_u ← invert(busy_u, day_start, day_end)
    free_common ← intersect(free_common, free_u)
    если free_common пуст: выход
вернуть [w для w in free_common если len(w) ≥ min_slot]
```

Сложность на неделю: `O(7 · U · S log S)`, где U — участники, S — слотов у одного. Для группы в 30 человек это микросекунды — оптимизация не нужна, кэш не нужен.

**Кворум** считается иначе — заметающей прямой: каждый свободный интервал даёт `+1` в начале и `−1` в конце, берутся участки со счётчиком ≥ порога, порог по умолчанию равен числу участников. При пороге = числу участников результат совпадает с пересечением; это зафиксировано отдельным тестом, чтобы две ветки не разъехались.

**Тепловая карта** — та же заметающая прямая по получасовым клеткам. Клетка считается свободной, только если человек свободен на всём её протяжении: полутонов нет намеренно, иначе цвет обманывает.

**Буфер на дорогу** применяется до `merge`: каждая занятость расширяется на `travel_buffer_min` с двух сторон. Побочный эффект намеренный — окно в 20 минут между парами при буфере 15 схлопывается и не предлагается как время встречи.

**Граничные случаи, которые обязаны быть в тестах:**
- смежные интервалы `9:00–10:00` и `10:00–11:00` → сливаются в один занятый блок, окна `10:00` не появляется;
- слот, выходящий за рабочее окно дня, обрезается, а не отбрасывается;
- пользователь без расписания → он не «свободен всегда», а исключён из расчёта и назван в выводе;
- пустой список пользователей → пустой результат, а не «все окна свободны»;
- окно короче `min_slot` (по умолчанию 30 мин) отсеивается;
- слот по чётности без заданного начала семестра — игнорируется, а не применяется к каждой неделе;
- кворум выше числа участников зажимается до «нужны все»;
- диапазон дат перекрывает только дни внутри себя.

## 7. Пользовательские сценарии

### 7.1. Сайт без Telegram

```
Лендинг → «Создать группу» (название + имя) → выдаётся кука-токен и ссылка /g/<slug>
        → редактор своей сетки → ссылка-приглашение уходит в чат группы
        → каждый открывает ссылку, представляется, отмечает пары
        → на дашборде тепловая карта, ползунок кворума, кнопка «Назначить»
```

### 7.2. Подключение чата в Telegram

```
Админ: добавляет бота в группу → /setup@QairuCoworkBot
Бот:   «Чат подключён» + кнопки:
       [📅 Заполнить расписание]  (deep-link t.me/bot?start=c-1001234)
       [👥 Кто уже заполнил]
Студент: жмёт кнопку → открывается личка → /start c-1001234
       → он привязан к чату → мастер ввода расписания
```

### 7.3. Ввод расписания — три пути

**Сетка** (сайт): рисуешь занятость мышью или пальцем; колонка дня заполняется кликом по заголовку.

**Импорт** (и сайт, и бот): человек присылает расписание как есть, парсер показывает разбор, и только после подтверждения оно сохраняется. **Никогда не сохраняет молча.**

**Мастер** (`/wizard` в боте): день недели кнопками → «продиктуй пары одной строкой» → подтверждение.

### 7.4. Встреча

На сайте — форма рядом со списком окон: кнопка «Назначить» под окном подставляет в неё
машинное время и человекочитаемую подпись.

В чате — мастер из трёх шагов на `ForceReply` (место → время → цель), затем карточка с
голосованием, где нажатие кнопки редактирует то же сообщение. «Предложить изменения»
открывает `ForceReply` для этого пользователя, его предложение дописывается в карточку.
Голосовать может любой из отмеченных; посторонним — всплывающее «эта встреча не для вас».

Черновик встречи живёт в `bot_state` с таймаутом 15 минут.

## 8. Устройство приложения на Next.js

### 8.1. Что где выполняется

| Маршрут | Тип | Почему так |
|---|---|---|
| `/`, `/g/[slug]`, `/g/[slug]/me`, `/g/[slug]/join` | серверные компоненты, `force-dynamic` | всё зависит от куки посетителя, кэшировать нечего |
| формы (создать группу, войти, встреча, голос, настройки) | server actions | никакого ручного `fetch` и параллельной схемы валидации |
| `/api/g/[slug]/state` | route handler | сетка перерисовывается при движении ползунка кворума без перезагрузки |
| `/g/[slug]/meetings/[id].ics` | route handler | адрес совпадает с прежней FastAPI-версией: ссылки из старых сообщений не ломаются (расширение остаётся частью сегмента и срезается в коде) |
| `/api/telegram/webhook` | route handler, Node | приёмник апдейтов |
| `proxy.ts` (бывший `middleware.ts`) | Node | единственное место, где можно поставить куку до рендера страницы |

### 8.2. Токен из персональной ссылки

`/g/<slug>?t=<token>` обрабатывает proxy: токен немедленно перекладывается в
`HttpOnly`-куку, а из адресной строки убирается редиректом — иначе он остался бы в истории
браузера, в заголовке `Referer` и на чужом скриншоте. Серверный компонент страницы куки
ставить не умеет, поэтому это именно proxy.

Константы куки вынесены в отдельный лёгкий модуль `cookies.ts`: proxy незачем тянуть
`config.ts` вместе с `node:crypto`.

### 8.3. Соединение с базой

`getDb()` создаёт соединение лениво и кэширует на `globalThis`. Лениво — потому что
`next build` импортирует модули страниц, чтобы их собрать, и падать там из-за отсутствующего
`DATABASE_URL` незачем: ошибка должна возникать в рантайме того запроса, которому база и правда нужна.

## 9. Что изменилось в поведении при переносе

Порт делался как перенос «один в один», и почти всё поведение совпадает с прежней версией.
Три осознанных отличия:

1. **`/busy 15.09-20.09 сессия` теперь занимает сутки, а не 15:09–20:09.**
   В разборе времени точка равноправна двоеточию, поэтому «15.09-20.09» само по себе выглядит
   как диапазон времени, и прежняя версия записывала час с небольшим каждый день — вопреки
   собственной документации, где эта строка приведена примером сессии на неделю. Теперь
   распознанные даты вырезаются из текста до поиска диапазонов времени. Заодно починилось
   «15.09-20.09 9:00-14:00 практика»: раньше сохранялись оба диапазона, теперь только 9:00–14:00.

2. **Напоминания рассылает cron, а не таймер в процессе.** Точность ограничена частотой
   запуска (на тарифе Hobby — раз в сутки). Флаг `meetings.reminder_sent` гарантирует, что
   одно напоминание не уйдёт дважды.

3. **`parity_from_iso_week` сохранена, но по-прежнему нигде не вызывается.** Это запасной
   вариант отсчёта чётности; продукт намеренно требует явную дату начала семестра.

## 10. Риски

| Риск | Митигация |
|---|---|
| Студенты не заполняют расписание | `/members` показывает пробел публично, `/remind` пингует; расписание вводится один раз и работает во всех чатах |
| Парсер не понял формат | всегда показывает разбор и просит подтвердить; при неудаче — сетка мышью или мастер по кнопкам |
| 403 при попытке написать в личку | ловится, в чат уходит кнопка «Начать диалог с ботом» |
| Флуд-лимиты Telegram | один агрегированный ответ вместо N сообщений |
| Смена username | упоминания через `tg://user?id=`, username обновляется при каждом апдейте |
| Приватность расписания | privacy mode включён, расписание видно только в агрегированном виде; `/clear` удаляет всё |
| Утечка персональной ссылки | токен из `?t=` немедленно перекладывается в `HttpOnly`-куку и редиректом убирается из адресной строки |
| Подделка входа через Mini App | подпись `initData` проверяется HMAC-ом от секрета, выведенного из токена бота, сравнение — постоянного времени, плюс проверка свежести `auth_date` |
| Подделка вызова вебхука | `X-Telegram-Bot-Api-Secret-Token`; секрет выводится из `BOT_TOKEN`, поэтому работает без отдельной настройки |
| Telegram зациклит повторы апдейта | вебхук отвечает `200` всегда, даже когда обработка упала: на любой другой ответ Telegram повторяет апдейт с нарастающей задержкой |
| Ответ бота длиннее 4096 символов | длинный список окон обрезается по границе строки с честной пометкой |
| Исчерпание соединений к базе | пулер Supabase в transaction mode, `max: 1` и `prepare: false` на функцию |
| Кворум маскирует, что кого-то нет | под каждым окном печатается `K/N` и поимённо те, кто занят |
| Локальная сборка уводит вебхук на localhost | `scripts/set-webhook.mjs` трогает вебхук только при `VERCEL_ENV=production` либо по явному `npm run bot:webhook` |
