# Нагрузочный тест: выдержит ли сайт

`npm run load` бьёт по сайту запросами с заданной параллельностью и печатает,
сколько запросов в секунду он выдерживает и с какими задержками. Без зависимостей:
генератор — `undici`, который уже есть в проекте.

```bash
npm run load -- --scenario mixed --ramp 5,10,20,50 --duration 20s
npm run load -- --help
```

## Сценарии

| сценарий | что делает |
|---|---|
| `board` | Главный путь чтения, с кукой входа: страница группы `/g/<код>`, «Моё расписание» `/g/<код>/me` и JSON доски `/api/g/<код>/state` (его доска запрашивает при каждом щелчке фильтра). Веса 2 : 1 : 2. |
| `save` | Сохранение личного расписания тем же запросом, что автосохранение редактора: `POST /api/g/<код>/schedule`, вся неделя целиком (2–3 пары в будни и одно «неудобно»). Заголовки как у браузера: `Origin` своего сайта (иначе `proxy.ts` отвечает 403) и `Sec-Fetch-Site: same-origin`. **Перезаписывает расписание аккаунта из куки.** |
| `bot` | Апдейты Telegram в вебхук `/api/telegram/webhook` с заголовком секрета: в личке `/start`, `/help`, просто текст; в группах `/join`, `/members`, `/free` (расчёт окон) и кнопка «кто заполнил». Люди и чаты выдуманные (id от 8·10¹⁵ — таких Telegram не выдаёт). Каждый апдейт идёт в базу. |
| `mixed` | Смесь, похожая на вечер перед парами: страницы 4 + 2, JSON доски 4, сохранение 1, бот 2. Без секрета вебхука или без бота на сервере — идёт без бота. |

Перед замером — проверка цели (`/api/healthz`, страница группы с кукой, пробный
апдейт) и прогрев: по три запроса каждого вида. Первый запрос прогрева печатается
отдельно — это холодный старт (загрузка кода, соединение с базой).

## Параметры

| | |
|---|---|
| `--target <url>` | куда; по умолчанию `http://localhost:3230` |
| `--scenario` | `board` \| `save` \| `bot` \| `mixed` |
| `--concurrency <n>` | одновременных запросов на одной ступени (по умолчанию 10) |
| `--ramp 5,10,20,50` | ступени параллельности — чтобы увидеть, где загибается |
| `--duration 20s` / `--requests 500` | длина ступени: временем или числом запросов |
| `--slug`, `--token` | группа и кука `qairu_token` участника (или `LOAD_SLUG`, `LOAD_TOKEN`) |
| `--bot-secret` | секрет вебхука (или `LOAD_BOT_SECRET`) |
| `--vercel-bypass` | секрет Protection Bypass for Automation превью (или `LOAD_VERCEL_BYPASS`) |
| `--timeout <мс>` | таймаут запроса, по умолчанию 15000 |
| `--no-warmup` | без прогрева — если нужен именно холодный старт |

Результат каждого прогона ложится JSON-ом в `.load/` (в git не попадает) —
удобно сравнивать «до» и «после» оптимизации.

## Безопасность

- **Telegram — никогда.** Адрес на `*.telegram.org` / `t.me` отвергается при любых флагах.
- **По умолчанию — только свой компьютер и превью.** `localhost`/`127.0.0.1` и
  `*.vercel.app` (кроме боевого) — без вопросов.
- **Боевой сайт и любой другой домен** — только с `--i-know-this-is-prod`, и тогда
  параллельность урезается до 5, ступень — до 30 с или 300 запросов. Боевым
  считается `https://qairu-cowork.vercel.app` и то, что в `NEXT_PUBLIC_SITE_URL` /
  `WEB_BASE_URL`.
- **Бот.** Без флага `bot` запускается только против локального
  `e2e-server.mjs … --fake-bot`: сервер пишет в `e2e/.state.json` случайный секрет
  вебхука, и тест сверяет его с тем, что отвечает сервер, — так он знает, что
  перед ним сервер с заглушкой Telegram. Против любого другого сервера нужен
  `--allow-real-bot`: бот там настоящий и на каждый апдейт пойдёт отвечать в
  `api.telegram.org` (в выдуманные чаты — Telegram ответит «chat not found», но
  запросы и лимиты бота настоящие).

## Локально

```bash
npx next build --webpack            # в git-worktree с node_modules-ссылкой Turbopack не собирает
node scripts/dev/e2e-server.mjs 3230 --fake-bot
# в другом окне
npm run load -- --scenario mixed --ramp 5,10,20,50
```

`e2e-server` поднимает PGlite в памяти с группой «ИС-21» и пишет в
`e2e/.state.json` код группы, куки двух участников (тест чередует обе) и — с
`--fake-bot` — секрет вебхука. С `--fake-bot` у сайта выдуманный `BOT_TOKEN`, а
`scripts/load/tg-blackhole.mjs` подменяет в процессе сайта `fetch`: всё, что идёт
на `api.telegram.org`, сразу получает ответ `{ok: true}`, в сеть не уходит ничего.
`LOAD_TG_DELAY_MS=150` перед запуском сервера добавит этим ответам задержку,
похожую на настоящий Telegram. Без `--fake-bot` бота нет: вебхук отвечает
`bot disabled`, не трогая базу, — `bot` откажется, `mixed` пойдёт без бота.

**Что значат локальные цифры.** PGlite принимает одно соединение
(`DATABASE_POOL_MAX=1`), поэтому все запросы стоят в очереди к нему, а сайт —
один процесс Node на вашем же компьютере вместе с генератором нагрузки. Это цифры
кода сайта: сколько стоит отрисовка страницы и расчёт окон, где лишние запросы к
базе. Ни Supabase, ни Vercel они не описывают.

## Против превью-деплоя (рекомендуется для инфраструктуры)

Инфраструктурные пределы видно только на настоящем Vercel и Supabase. Чтобы не
трогать живых людей:

1. **Отдельный проект Supabase** (бесплатный, второй в аккаунте): выполнить
   миграции `drizzle/` по порядку, как в DEPLOY.md, шаг 2. Строка — пулер
   (Transaction, порт 6543).
2. **Превью на Vercel** с этой базой: в Settings → Environment Variables задать
   `DATABASE_URL` только для окружения **Preview** (или для одной ветки).
   `BOT_TOKEN` для Preview **не задавать**: вебхук превью сборка и так не
   регистрирует (`scripts/set-webhook.mjs` — только production), но с боевым
   токеном превью слало бы через живого бота напоминания и ответы. Без него
   `bot` на превью мерить нечего, и это нормально: путь бота — та же база и тот
   же код, его меряют локально.
3. **Пропуск через защиту превью.** Превью по умолчанию закрыто входом Vercel
   (тест получит 401). Settings → Deployment Protection → Protection Bypass for
   Automation → создать секрет и передать `--vercel-bypass <секрет>`.
4. **Данные.** Открыть превью, войти (через Telegram-вход на превью нужен бот —
   проще создать группу и аккаунт на сайте), заполнить расписание, взять из
   DevTools → Application → Cookies значение `qairu_token` и код группы из адреса.
   Нужен аккаунт Telegram-типа (`save` и JSON доски пускают только их) — либо
   положить сессию в базу превью руками, как это делает `scripts/dev/e2e-server.mjs`
   (`web_sessions.token_hash` = sha256 токена).

```bash
LOAD_TOKEN=… npm run load -- --target https://qairu-cowork-git-load-….vercel.app \
  --slug abcd1234 --vercel-bypass … --scenario board --ramp 5,10,20,50
```

## На что смотреть

- **p95** — 95% запросов быстрее этого. Средняя скрывает хвост, p95 — то, что
  чувствует каждый двадцатый. Пороги вердикта: ≤ 800 мс — «ДЕРЖИТ», ≤ 2 с —
  «ТЕРПИМО», больше — «МЕДЛЕННО».
- **Ошибки** по кодам: больше 1% — ступень провалена. `307` — кука не подошла
  (редирект на вход), `403` — Origin/членство, `5xx` — сервер упал, `timeout`,
  `refused`/`reset` — сервер не принимает соединения. У вебхука ошибки обработки
  не видны снаружи (он всегда отвечает 200, чтобы Telegram не повторял апдейт), —
  смотрите лог сервера: `qairu: ошибка при обработке апдейта`.
- **Где загиб.** Тест ищет первую ступень, на которой rps вырос меньше чем на 15%
  при большей параллельности (запросы встали в очередь) или p95 вырос вдвое.
  Дальше этой точки добавлять людей — только растить ожидание.

Что обычно упирается первым на бесплатных тарифах:

- **Пулер Supabase.** У бесплатного проекта пул соединений пулера к базе
  небольшой (Database → Settings → Connection pooling, Pool Size; на Free — порядка
  15–20), а каждый экземпляр функции держит до 5 (`src/db/client.ts`). Когда
  экземпляров много, запросы ждут свободного соединения: p95 растёт ступенькой,
  потом приходят ошибки `timeout`/`5xx` с `too many clients` или
  `MaxClientsInSessionMode` в логах Vercel.
- **Функции Vercel.** Холодный старт — первый запрос нового экземпляра (видно в
  прогреве и в p99). При всплеске Vercel поднимает новые экземпляры — каждый
  холодный и со своими соединениями к базе. Hobby ограничивает месячные квоты
  (вызовы, CPU, трафик — Usage в панели Vercel), а защита от DDoS может начать
  отвечать 429 или челленджем на поток с одного адреса — это не сайт упал.
- **Сам код.** Если локально p95 высокий уже на малой параллельности — дело не в
  инфраструктуре: смотрите страницу с большим p95 в таблице «По запросам».

## Почему не по боевому

Боевой сайт делит с живыми людьми всё: функции и месячные квоты Vercel Hobby,
пул соединений и трафик Supabase Free, лимиты Telegram-бота. Тест, который нашёл
загиб, в этот момент и уронил сайт для всех. `save` к тому же перезаписывает
расписание аккаунта, а бот с настоящим токеном шлёт запросы в Telegram. Поэтому
боевой — только с `--i-know-this-is-prod`, при малой параллельности и для
проверки «живо ли», а не для поиска предела.
