# Деплой QairuCowork: сайт + телеграм-бот

Пошаговый план с нуля до работающего бота. Считаем, что не сделано ещё ничего:
нет ни репозитория, ни базы, ни бота.

**Времени нужно:** ~40 минут, из них половина — ожидание сборки.
**Денег:** 0 ₸. Vercel Hobby и Supabase Free покрывают всё, что здесь описано.

---

## Главное, что нужно понять до начала

**Бот — это не отдельная программа.** Не нужно арендовать сервер, ставить туда
Python и держать процесс включённым. Бот живёт внутри сайта как один обычный
адрес: `/api/telegram/webhook`. Телеграм сам стучится в этот адрес, когда кто-то
пишет боту.

Отсюда весь план:

```
                       ┌──────────────────────────┐
   пользователь ──────►│  Vercel (один проект)    │
   в браузере          │                          │
                       │   /g/abc123   — сайт     │
   пользователь ──────►│   /api/telegram/webhook  │
   в телеграме         │               — бот      │
                       └────────────┬─────────────┘
                                    │
                            ┌───────▼────────┐
                            │   Supabase     │
                            │  (PostgreSQL)  │
                            └────────────────┘
```

**Один деплой = и сайт, и бот сразу.** Завести нужно три вещи: репозиторий на
GitHub, базу в Supabase, проект в Vercel. Плюс самого бота у BotFather.

## Шаг 2. База данных в Supabase

**2.1. Создать проект**

[supabase.com](https://supabase.com) → **New project**.

- Name: `qairu-cowork`
- Database Password: сгенерировать и **сразу сохранить** — второй раз его не покажут.
- Region: ближайший к пользователям (`eu-central-1` для Казахстана — разумный выбор).

Создание занимает 1–2 минуты.

**2.2. Скопировать строку подключения — именно пулер**

**Project Settings → Database → Connection pooling → Transaction**, порт **6543**.

Строка выглядит так:

```
postgresql://postgres.abcdefgh:ПАРОЛЬ@aws-0-eu-central-1.pooler.supabase.com:6543/postgres
```

Подставьте в неё пароль из шага 2.1 вместо слова `ПАРОЛЬ`.

> **Почему пулер, а не прямое подключение (порт 5432).** На Vercel каждый запрос
> обслуживает отдельная функция, и каждая открыла бы своё соединение с базой.
> Лимит соединений кончится раньше, чем трафик. Пулер держит соединения за них.
>
> Если в пароле есть символы `@ : / ? # &` — их надо закодировать (`@` → `%40`),
> иначе строка подключения разберётся неправильно.

**2.3. Создать таблицы**

**SQL Editor → New query** → вставить целиком содержимое файла
[`drizzle/0000_init.sql`](drizzle/0000_init.sql) из проекта → **Run**.
Затем так же, отдельными запросами, — [`drizzle/0001_admin_login.sql`](drizzle/0001_admin_login.sql)
[`drizzle/0002_avatars.sql`](drizzle/0002_avatars.sql), [`drizzle/0003_real_name.sql`](drizzle/0003_real_name.sql),
[`drizzle/0004_recurring_meetings.sql`](drizzle/0004_recurring_meetings.sql),
[`drizzle/0005_calendar_and_summary.sql`](drizzle/0005_calendar_and_summary.sql),
[`drizzle/0006_meeting_duration.sql`](drizzle/0006_meeting_duration.sql),
[`drizzle/0007_row_level_security.sql`](drizzle/0007_row_level_security.sql),
[`drizzle/0008_session_token_hash.sql`](drizzle/0008_session_token_hash.sql),
[`drizzle/0009_attendance_and_origin.sql`](drizzle/0009_attendance_and_origin.sql),
[`drizzle/0010_owner_console.sql`](drizzle/0010_owner_console.sql)
и [`drizzle/0011_owner_users.sql`](drizzle/0011_owner_users.sql).

Миграции выполняются **по порядку номеров** и **каждая один раз**. Если база уже
работает на прошлой версии (`0000` выполнен давно), при обновлении нужно выполнить
только `0001_admin_login.sql`: он добавит роли участников, вход по паролю и
уведомления на сайте, а создателем каждой старой группы с сайта сделает её
первого участника. `0002_avatars.sql` добавляет таблицу фото профиля, `0003_real_name.sql` — колонку настоящего имени,
`0004_recurring_meetings.sql` — повторяющиеся встречи (колонки `repeat_until` и `reminded_start` у `meetings`),
`0005_calendar_and_summary.sql` — подписку на личный календарь (`calendar_url`, `calendar_synced_at`,
`calendar_error` у `users`) и итоги встреч (`summary`, `summary_by`, `summary_at` у `meetings`),
`0006_meeting_duration.sql` — длительность встречи (`duration_min` у `meetings`),
`0007_row_level_security.sql` — включает RLS на всех таблицах. Политик нет намеренно:
сайт ходит в базу владельцем таблиц (роль `postgres`), на него RLS не действует, а Data API
Supabase с публичным ключом проекта не видит ни строки. После неё **Advisors → Security
Advisor** больше не ругается на «RLS disabled in public»,
`0008_session_token_hash.sql` — токены сессий хранятся только хешем (`token_hash` вместо
`token` у `web_sessions`); уже выданные куки продолжают работать, сессии без заходов
дольше 30 дней удаляются,
`0009_attendance_and_origin.sql` — таблица `meeting_attendance` («был ли ты на встрече»: бот
спрашивает после встречи, на сайте — кнопки у прошедшей) и колонки `origin` и `ext_version` у
`schedule_state` (откуда расписание: вручную, с фото, из кампуса — видно старосте и в консоли `/admin`),
`0010_owner_console.sql` — консоль владельца `/admin`: таблицы `owner_login_codes` (одноразовые
коды от бота — только HMAC-хеш), `owner_sessions` (сессии консоли — только SHA-256 токена) и
`owner_audit` (журнал входов, адрес и браузер — только ключевым хешем), все под RLS. Старые
данные она не трогает; без неё падает только `/admin`,
`0011_owner_users.sql` — вкладки «Пользователи» и «Группы» консоли: колонка `target_id` у
`owner_audit` (чью карточку открыл владелец — журнал просмотров) и индекс `ix_memberships_user_id`
(«мои группы» на каждой странице и карточка человека ищут участие по человеку). Обе операции
быстрые и данных не меняют; без неё падают карточки людей и групп в `/admin` и вкладка «Система».

> **Миграцию выполнять до того, как новый код попадёт на Vercel.** Код с новыми
> колонками на старой базе падает на любой странице со встречами. Теперь это
> ловит сама сборка: `scripts/check-schema.mjs` сверяет базу с файлами `drizzle/`
> и, если чего-то не хватает, роняет сборку с сообщением, какой файл выполнить, —
> на сайте при этом остаётся прошлая версия.

✅ **Готово, когда:** в **Table Editor** появились таблицы `users`, `chats`,
`memberships`, `busy_slots`, `meetings`, `credentials`, `notices`, `avatars` и остальные.

## Шаг 5. Подключить бота к сайту

Здесь **важен порядок**: вебхук регистрируется во время сборки, поэтому токен
должен появиться в Vercel *до* неё.

**5.1. Добавить токен**

**Vercel → проект → Settings → Environment Variables → Add New**:

| Name | Value | Окружения |
|---|---|---|
| `BOT_TOKEN` | токен из шага 4.1 | Production (и Preview, если заведёте отдельного тестового бота) |

**5.2. Пересобрать проект**

**Deployments → последний деплой → «…» → Redeploy.**

Во время сборки скрипт `scripts/set-webhook.mjs` сам:

- пропишет Телеграму адрес `https://ваш-адрес.vercel.app/api/telegram/webhook`;
- выведет секрет заголовка из токена (отдельная переменная не нужна);
- загрузит меню команд — отдельно для личных чатов и для групп.

В логе сборки появится строка:

```
[qairu:webhook] вебхук зарегистрирован: https://…/api/telegram/webhook (бот @qairu_cowork_bot)
```

> **Вебхук ставится только на продакшен-сборке.** Превью-деплои получают новый
> адрес на каждый коммит; если бы они перехватывали вебхук, рабочий бот
> отваливался бы после каждого пуша в ветку.

✅ **Проверка бота:**

1. Открыть бота в Телеграме → `/start` → приходит приветствие;
2. `/schedule` → бот отвечает кнопкой «Открыть сайт» (расписание вносится на сайте);
3. Создать тестовую группу, добавить туда бота, выдать ему права администратора,
   отправить `/setup` → бот подключает чат и присылает ссылку на сайт;
4. `/availability` в группе → бот показывает общие свободные окна.

## Шаг 6. Напоминания о встречах и обновление календарей (cron)

Адрес `/api/cron/reminders` рассылает напоминания о встречах, после конца встречи
спрашивает «был ли ты» и на остаток времени обновляет подключённые личные
календари (не чаще раза в 3 часа на человека). Отвечает сразу — `202
{"ok":true,"accepted":true}`, а сама работа идёт уже после ответа, до 300 секунд
(бюджет 250 с + запас). Итог прогона — в консоли владельца («последний прогон
cron») и в **Runtime Logs** строкой `[qairu:cron] {...}`.

Кто его вызывает — три источника, все с одним секретом `CRON_SECRET` в заголовке
`Authorization: Bearer …`:

- **Внешний пингер cron-job.org раз в 5 минут — основной.** Только он даёт
  регулярность, на которой держится «напомнить за 30 минут».
- **GitHub Actions** ([`.github/workflows/reminders.yml`](.github/workflows/reminders.yml)) —
  дубль на случай, если пингер отвалится. Расписание GitHub **не гарантировано**:
  в октябре 2026 запуски «раз в 10 минут» на деле приходили 2–5 раз в сутки, а через
  60 дней без коммитов GitHub выключает воркфлоу совсем.
- **Vercel** раз в сутки ([`vercel.json`](vercel.json)) — на Hobby чаще нельзя.

Одновременные вызовы безопасны: каждое напоминание, вопрос «был ли ты» и календарь
забираются атомарной отметкой в базе до отправки — два прогона не пришлют одно и то
же дважды, а поделят работу.

**Один раз завести общий секрет:**

1. Придумать случайную строку (например, `openssl rand -hex 32` или любой
   генератор паролей) — это `CRON_SECRET`.
2. **Vercel → Settings → Environment Variables** → `CRON_SECRET` = эта строка,
   окружение Production → **Redeploy**.
3. **GitHub → репозиторий → Settings → Secrets and variables → Actions →
   New repository secret** → имя `CRON_SECRET`, значение — та же строка.
4. Если адрес сайта не `https://qairu-cowork.vercel.app` — там же, во вкладке
   **Variables**, завести `SITE_URL` со своим адресом.

Проверка: **GitHub → Actions → Reminders → Run workflow** — шаг должен
закончиться ответом `{"ok":true,"accepted":true}`. Без секрета в GitHub запуск
**красный** (раньше он молча выходил с успехом и прятал поломку).

### Внешний пингер (cron-job.org)

Бесплатно, до раза в минуту, свои заголовки, письмо при сбоях. Таймаут у него 30 с —
поэтому адрес и отвечает сразу, не дожидаясь рассылки.

1. Зарегистрироваться на [cron-job.org](https://cron-job.org) → **Cronjobs → Create cronjob**.
2. **Title** — `QairuCowork reminders`; **URL** — `https://qairu-cowork.vercel.app/api/cron/reminders`
   (или свой адрес сайта).
3. **Execution schedule** — **Every 5 minutes**.
4. Вкладка **Advanced**:
   - **Request method** — `GET`;
   - **Headers → Add** — ключ `Authorization`, значение `Bearer <CRON_SECRET>`
     (слово `Bearer`, пробел и та же строка, что в Vercel);
   - **Timeout** — 30 секунд (максимум бесплатного тарифа, ответ приходит за доли секунды);
   - **Treat redirects with HTTP 3xx status code as success** — выключить: редирект
     значит, что адрес неверный (например, `http://` вместо `https://`).
5. **Notifications** — включить письмо «on failure» (и «when the job is disabled»).
6. **Save** → в списке нажать **Test run**: ответ `202` с телом
   `{"ok":true,"accepted":true}`. `401` — секрет в заголовке не совпадает с Vercel;
   `503` — в Vercel нет `CRON_SECRET` (или не сделан Redeploy).
7. Через 10–15 минут открыть консоль владельца `/admin`: «последний прогон cron» должен
   быть свежим. Секрет в адрес (`?secret=`) не ставить — адрес не примет его, а
   адреса оседают в журналах.

GitHub Actions после этого не выключать — он остаётся дублем.

## Шаг 7. По желанию: свой домен и вход одним касанием

**Свой домен.** **Vercel → Settings → Domains** → добавить домен → прописать
DNS-записи, которые покажет Vercel. После этого добавить переменную
`NEXT_PUBLIC_SITE_URL=https://ваш-домен` и **сделать Redeploy** — иначе вебхук и
ссылки в сообщениях бота останутся на старом адресе `*.vercel.app`.

**Кнопка-меню (Mini App).** Если открыть сайт прямо из Телеграма, человек
опознаётся автоматически: расписание из бота и с сайта оказывается одним и тем же,
без входа по ссылке. У BotFather:

```
/setmenubutton → выбрать бота → указать https://ваш-адрес.vercel.app
```

Без этого всё работает тоже — просто на сайт заходят по ссылке-приглашению.

**Вступление в одно касание (главное мини-приложение).** У BotFather:
**/mybots → бот → Bot Settings → Configure Mini App → Enable Mini App** → адрес
сайта. После этого кнопка «Заполнить расписание» под сообщениями бота в группе
открывает группу сразу в Telegram — без лички с ботом и Start, — а на странице
группы (вкладка «Участники») появляется «Ссылка для Telegram» вида
`https://t.me/<бот>?startapp=<код>`. Сайт замечает включение сам в течение
6 часов, сразу — после `https://<адрес сайта>/api/telegram/setup?secret=СЕКРЕТ`
(см. таблицу поломок).

## Шаг 8. По желанию: консоль владельца `/admin`

Статистика, люди и группы, состояние бота и cron, размер базы и журнал входов — только для владельца.

1. Выполнить в Supabase `drizzle/0010_owner_console.sql` и `drizzle/0011_owner_users.sql`
   (**сначала SQL, потом пуш**).
2. **Vercel → Settings → Environment Variables**: `ALERT_CHAT_ID` = свой Telegram id
   (бот подскажет его командой `/id` в личке) и, если хочется отдельный ключ,
   `OWNER_CONSOLE_SECRET` = случайная строка (`openssl rand -hex 32`). Окружение —
   Production → **Redeploy**.
3. Войти на сайт через Telegram, открыть `/admin` → «Прислать код» → бот пришлёт 6 цифр
   в личку → ввести. Сессия консоли живёт 12 часов; о каждом входе бот пишет в `ALERT_CHAT_ID`.

Вкладки: «Обзор» (`/admin` — сводка, воронка, удержание по неделям, языки, рост групп,
функции, охват бота), «Пользователи» (`/admin/users` — поиск, фильтры, порядок, страницы;
карточка — `/admin/users/<id>`), «Группы» (`/admin/groups`, карточка — `/admin/groups/<id>`),
«Система» (`/admin/system` — бот, cron, деплой, «Качество за 24 часа», хранилище, журнал входов
и просмотров). «Качество» — p50/p95 времени ответа вебхука, доски группы, её обновления, сохранения
расписания и вызовов Telegram; задержка напоминаний и сколько опоздало больше чем на 5 минут или не
дошло; сбои Telegram по классам (403, 429, таймаут/сеть, прочее); прогоны cron, самый долгий перерыв
между ними и упёршиеся в бюджет — рядом то же за 7 дней. Хранятся только часовые счётчики в
`bot_state` (миграции не нужно), 8 дней; выключить запись — `QAIRU_METRICS=off`.
Каждый просмотр карточки пишется в журнал (`owner_audit`, событие `user_view` / `group_view`).

Всем остальным `/admin` и все его вкладки отвечают «не найдено». В `robots.txt` адрес намеренно не вписан:
файл публичный и сам назвал бы его; поисковики страницу и так не видят — она отдаёт
404 всем, кроме владельца, а ему — `noindex`.

## Шаг 9. Мониторинг

Чтобы о поломке первым узнавал владелец, а не пользователи. Две бесплатные проверки,
обе пишут в Telegram:

- **сайт и база** — внешний монитор раз в 5 минут открывает `/api/healthz`;
- **cron напоминаний** — после каждого прогона сайт сам стучится в healthchecks.io
  («пульс»); нет пульса 20 минут — тревога.

`/api/healthz` делает в базу один `select 1` с таймаутом 2,5 с и отвечает:

| Ответ | Значит |
|---|---|
| `200 {"ok":true,"db":{"ok":true,"ms":42},"version":"b046073","at":"…"}` | сайт и база живы; `version` — коммит на проде |
| `503 {"ok":false,"db":{"ok":false,"ms":2500,"error":"timeout"},…}` | база не ответила за 2,5 с (`"error":"unavailable"` — ответила ошибкой; причина — в Runtime Logs строкой `[qairu:healthz]`) |

`/api/healthz?live` — то же без похода в базу (жив ли сам сайт). Ответ не кешируется
и ничего личного не содержит: адрес публичный.

### Сайт: UptimeRobot

1. Зарегистрироваться на [uptimerobot.com](https://uptimerobot.com) (Free — 50 мониторов,
   проверка раз в 5 минут).
2. Сначала канал тревог: **Integrations** (в старом интерфейсе **My Settings → Alert
   Contacts**) → **Telegram** → **Add** → открыть ссылку на бота UptimeRobot → **Start**.
   Тревоги можно слать и в группу: добавить туда того же бота. Если Telegram на
   бесплатном тарифе недоступен — оставить e-mail.
3. **New monitor** → тип **HTTP(s)**; **URL** — `https://qairu-cowork.vercel.app/api/healthz`
   (или свой адрес); **Interval** — 5 minutes.
4. В **Notifications** отметить Telegram (и e-mail) → **Create monitor**.
5. Проверка: монитор становится зелёным **Up** в течение пары минут. Монитор считает
   падением всё, кроме 2xx, — то есть и `503` от упавшей базы.

### Cron напоминаний: healthchecks.io

1. Зарегистрироваться на [healthchecks.io](https://healthchecks.io) (Free — 20 проверок).
2. **Add Check** → **Name** — `QairuCowork cron`; **Schedule** — Simple: **Period**
   5 minutes, **Grace** 15 minutes → **Save**. Скопировать **Ping URL** вида
   `https://hc-ping.com/<uuid>`.
3. **Integrations → Telegram → Add Integration** → откроется бот `@HealthchecksBot` →
   **Start** (или добавить его в группу) → в чате придёт подтверждение. Включить эту
   интеграцию у проверки (страница проверки → **Notification Methods**).
4. **Vercel → Settings → Environment Variables** → `HEALTHCHECKS_PING_URL` = скопированный
   адрес, окружение Production → **Redeploy**. Только `https://` — иначе пульс не уходит.
5. Проверка: через 5–10 минут проверка в healthchecks.io зелёная (**up**), в списке
   **Events** — пинги после каждого прогона cron.

Как читать тревоги: прогон упал (ошибка базы и т. п.) — сайт шлёт `<адрес>/fail`, и
проверка краснеет сразу; пульса нет дольше 20 минут — не дошёл ни один вызов cron
(отвалился пингер cron-job.org, разъехался `CRON_SECRET`) или прогоны не доживают до
конца. Адрес пульса — сам себе пароль: в репозиторий и чаты его не класть.

### После каждого деплоя: проверка прода

[`.github/workflows/smoke.yml`](.github/workflows/smoke.yml) запускается сам, когда Vercel
сообщает GitHub, что деплой на Production готов. Он ждёт, пока `/api/healthz` покажет
новый коммит, и проверяет как гость: главная — `200`, `/api/healthz` — `200` с живой
базой, `/admin` — `404`, `/extension` — `200`, `/api/cron/reminders` без секрета — `401`.
Провал — красный крестик у коммита и письмо от GitHub. Настраивать ничего не нужно;
руками — **Actions → Smoke → Run workflow**, локально — `node scripts/smoke.mjs`.

### Качество и нагрузка

Время ответа бота и страниц, задержка напоминаний, сбои Telegram и прогоны cron за сутки
и неделю — в консоли владельца, вкладка **«Система» → «Качество за 24 часа»**. Выдержит
ли сайт нагрузку — `npm run load` (сценарии, безопасный запуск и как читать цифры — в
[scripts/load/README.md](scripts/load/README.md)). Гонять по превью-деплою с отдельной
базой, не по проду.

## Переменные окружения: полный список

| Переменная | Обязательна | Зачем |
|---|---|---|
| `DATABASE_URL` | **да** | подключение к Supabase, обязательно пулер (порт 6543) |
| `ALERT_CHAT_ID` | нет | куда бот шлёт алерты об ошибках сайта и о входах в консоль: свой id (напиши боту `/id` в личке) или id рабочей группы (`/id` в ней). Свой id здесь же делает тебя владельцем (консоль `/admin`). Без переменной алертов нет |
| `OWNER_IDS` | нет | ещё владельцы через запятую (`123,456`) — нужно, если `ALERT_CHAT_ID` указывает на группу. Владелец открывает `/admin`, остальным там «не найдено» |
| `OWNER_CONSOLE_SECRET` | нет | ключ HMAC консоли владельца: им хешируются коды входа и адреса в журнале. По умолчанию выводится из `BOT_TOKEN`; отдельная случайная строка (`openssl rand -hex 32`) разводит секреты. Смена ключа гасит только живые коды (они и так на 5 минут) |
| `DATABASE_POOL_MAX` | нет | соединений с пулером на экземпляр функции, по умолчанию 5; локальной базе на PGlite — 1 |
| `BOT_TOKEN` | для бота | токен от BotFather; без него сайт работает, бота нет |
| `NEXT_PUBLIC_SITE_URL` | нет | только если свой домен или локальный туннель |
| `TELEGRAM_WEBHOOK_SECRET` | нет | по умолчанию выводится из `BOT_TOKEN` |
| `CRON_SECRET` | для напоминаний | общий секрет с внешним пингером и GitHub Actions (шаг 6); без него адрес cron отвечает 503 и напоминания не уходят |
| `HEALTHCHECKS_PING_URL` | нет | адрес пульса cron в healthchecks.io (`https://hc-ping.com/…`, шаг 9): после удачного прогона напоминаний сайт стучится туда, после упавшего — на `…/fail`. Только `https`; пусто — пульса нет |
| `DEFAULT_TZ` | нет | пояс консоли владельца `/admin` (время входов и прогонов); по умолчанию `Asia/Almaty`. Сайт и бот живут в поясе группы, эта переменная их не трогает |

**Пустое значение = переменная не задана.** Vercel хранит пустые строки как есть
(например, если вставить `.env.example` целиком). Код читает переменные через `env()`
(`src/lib/config.ts`, `scripts/env.mjs`): пустая строка или одни пробелы дают значение
по умолчанию и не перекрывают следующую по цепочке — пустой `NEXT_PUBLIC_SITE_URL`
не пропускает `WEB_BASE_URL`.
Прямое чтение `process.env.X` в `src/` и `scripts/` запрещает линтер. Ненужную
переменную в Vercel лучше удалить, чем оставлять пустой.

## Если что-то не работает

| Симптом | Причина и что делать |
|---|---|
| Сайт открылся, но группа не создаётся | Неверный `DATABASE_URL` или не выполнен `0000_init.sql`. Смотреть Runtime Logs в Vercel |
| `/api/healthz` отвечает `503` | База не ответила за 2,5 с или ответила ошибкой. Причина — в Runtime Logs строкой `[qairu:healthz]`; чаще всего неверный `DATABASE_URL`, пауза проекта Supabase или сбой у Supabase (status.supabase.com) |
| Страница группы падает с ошибкой про `role`, `created_by`, `credentials` или `notices` | Не выполнена миграция `0001_admin_login.sql` |
| Фото профиля не сохраняется («Не удалось загрузить фото») | Не выполнена миграция `0002_avatars.sql` |
| Сайт падает с ошибкой про `real_name` | Не выполнена миграция `0003_real_name.sql` |
| Страница группы или бот падают с ошибкой про `repeat_until` или `reminded_start` | Не выполнена миграция `0004_recurring_meetings.sql` |
| Страница группы или бот падают с ошибкой про `duration_min` | Не выполнена миграция `0006_meeting_duration.sql` |
| Все разом оказались не вошедшими, в логах ошибка про `token_hash` | Не выполнена `0008_session_token_hash.sql`: код новый, а база старая. Выполнить её — куки снова пустят |
| Падают страницы группы и сохранение расписания, в логах `meeting_attendance` или `origin` | Не выполнена `0009_attendance_and_origin.sql`. Выполнить её в SQL Editor |
| `/admin` падает с ошибкой про `owner_login_codes`, `owner_sessions` или `owner_audit` | Не выполнена `0010_owner_console.sql`. Выполнить её в SQL Editor — остальной сайт от неё не зависит |
| Карточки людей и групп в `/admin` или вкладка «Система» падают с ошибкой про `target_id` | Не выполнена `0011_owner_users.sql`. Выполнить её в SQL Editor (сборка с `DATABASE_URL` это и так поймает) |
| В `/admin` «не найдено», хотя вошёл | Твоего Telegram id нет ни в `ALERT_CHAT_ID`, ни в `OWNER_IDS` (id группы со знаком минус владельцем не считается), либо вход на сайт был не через Telegram. Добавить id в Vercel → Redeploy |
| Код для консоли не приходит | Нет `BOT_TOKEN`, бот у тебя в личке не запущен (открой его, нажми Start) или исчерпан лимит: 3 кода за 15 минут, 10 неверных вводов за час закрывают вход до конца часа |
| Вошёл в консоль, но по ссылке из Telegram она снова просит код | Кука консоли — SameSite=Strict: браузер не прикладывает её к переходу с чужого сайта. Обнови страницу |
| Сборка падает с `[qairu:schema] Не включён RLS: …` | Не выполнена `0007_row_level_security.sql`. Выполнить её в Supabase и сделать Redeploy |
| Сборка падает с `[qairu:schema] В базе не хватает: …` | Не выполнена миграция, которую называет сообщение (например, `0005_calendar_and_summary.sql`). Выполнить её в Supabase и сделать Redeploy |
| Сборка падает с `You are using Node.js … For Next.js, Node.js version ">=20.9.0" is required` | Next 16 требует Node 20.9 или новее: **Vercel → Settings → Build and Deployment → Node.js Version** → 22.x или новее, затем Redeploy |
| `too many connections` в логах | Взято прямое подключение (5432) вместо пулера (6543). Заменить строку и сделать Redeploy |
| Бот молчит на `/start` | Вебхук не зарегистрирован: `BOT_TOKEN` добавлен, но Redeploy не сделан. Проверить: `https://api.telegram.org/botТОКЕН/getWebhookInfo` — там должен быть ваш адрес и пустой `last_error_message` |
| Бота нельзя добавить в группу | Не сделан `/setjoingroups → Enable` у BotFather |
| Бот в группе не отвечает на команды | Не отправлен `/setup`, либо у бота нет прав администратора |
| Адрес сайта поменялся, бот отвечает на старом | Зарегистрировать вебхук без пересборки: `https://новый-адрес/api/telegram/setup?secret=СЕКРЕТ`. Секрет — первые 48 hex-символов от `sha256("qairu-webhook:" + BOT_TOKEN)`; его печатает `npm run bot:webhook` |
| Напоминания не приходят | Открыть `/admin` → «последний прогон cron». Давно не было — не настроен или отключён пингер cron-job.org (шаг 6; письмо о сбое приходит на почту) и выключен воркфлоу Reminders. Ответ 503 — нет `CRON_SECRET` в Vercel, 401 — секрет у пингера или в GitHub не совпадает. Прогоны идут, но напоминаний нет — в **Runtime Logs** строка `[qairu:cron]`: `"ok":false` с ошибкой или `"deferred"` > 0 (не уложились в бюджет, остальное уйдёт следующим прогоном) |
| Календарь не подключается | Нужна ссылка iCal (.ics), которая открывается без входа: в Google — «Секретный адрес в формате iCal». Ссылки во внутреннюю сеть сайт не загружает намеренно |

**Где смотреть логи:** Vercel → проект → **Deployments** → нужный деплой →
**Runtime Logs** (ошибки бота и сайта) и **Build Logs** (ошибки сборки и вебхука).

## Как обновлять дальше

```powershell
git add .
git commit -m "что изменилось"
git push
```

Vercel соберёт и выкатит сам, вебхук перерегистрируется в той же сборке.
Каждый пуш проверяет GitHub Actions ([`ci.yml`](.github/workflows/ci.yml)): типы,
линтер, тесты, сборка и сквозные тесты в браузере. Красная проверка на GitHub —
повод не ждать, пока сломается прод. А после выката живой сайт проверяет
[`smoke.yml`](.github/workflows/smoke.yml) (шаг 9). Локально то же самое:

```powershell
npm run typecheck; npm run lint; npm test
npx next build; npm run e2e
```

**Изменения в схеме базы:** `npm run db:generate` создаёт новый SQL-файл в
`drizzle/`; его нужно выполнить в Supabase SQL Editor вручную — Vercel миграции
сам не накатывает. Новой таблице в `src/db/schema.ts` нужен `.enableRLS()` — иначе
упадёт тест `tests/schema.test.ts`.

**Резервная копия.** На бесплатном тарифе Supabase не делает бэкапы, которые можно
скачать. Перед большой миграцией стоит снять копию самому: нужен `pg_dump` той же
или более новой версии, что и Postgres в Supabase, а строка подключения — та же, что
в `DATABASE_URL`, только порт **5432** вместо 6543 (дампу нужен сеансовый режим пулера):

```powershell
pg_dump "<DATABASE_URL с портом 5432>" --no-owner -f qairu-backup.sql
```

Файл хранить у себя, не в репозитории: в нём все данные пользователей. Проект Supabase
Free засыпает после 7 дней без запросов — каждый прогон cron напоминаний обращается к
базе, так что пингер раз в 5 минут (и даже суточный cron Vercel) этого не допускает.
